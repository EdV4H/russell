# 0006. 装備は MCP 以外の接続も許す（最初の装備は HTTP で繋ぐ）

- 状態: 採用
- 日付: 2026-08-11
- 関連: [`../concepts/14-equipment.md`](../concepts/14-equipment.md)、
  [`../concepts/15-policy-gate-and-security.md`](../concepts/15-policy-gate-and-security.md)、
  [`../reference/30-russell-plugin-contract.md`](../reference/30-russell-plugin-contract.md)

## 文脈

装備は「**MCP接続 + scope + danger_level + 効果分類**」と定義されている（§9.1）。
`EquipmentDefinition` にも `mcpServer: McpServerRef` が必須で入っている——ただし型は
`unknown // McpServerRef（実装時に確定）`のまま、**実装される装備が1つも無い**状態だった。

最初の装備として「Notion を読む」を作るにあたって、公式の Notion MCP サーバーを使うか、
HTTP API を直接叩くかを決める必要が出た。

## 決定

**装備の本質は「MCP で繋ぐこと」ではなく、`scope`・`danger_level`・効果分類を伴って
Policy Gate の管理下に入ることである。** 接続方式は装備プラグインの実装詳細として扱い、
MCP 以外（HTTP・SDK・ローカルプロセス）も許す。

- `equipment-notion` は Notion の HTTP API を直接叩く。読み取り2ツールだけを register する
- `mcpServer` は接続先の記述として残すが、MCP サーバーであることを要求しない
- 装備が満たすべきものは変わらない: 効果分類の申告、スコープの宣言、danger_level、
  そして**コアが強制する原値（未登録=deny / killswitch / fail-closed）の下に入ること**

## 検討した他の案

### A. 公式 Notion MCP サーバーを使う（設計の字面どおり）

MCP の疎結合思想に乗れるし、ツール定義が向こうから来るので実装量も減る。
**採らなかったのは、書き込みツールが一緒に生えてくるから**。

Notion の MCP サーバーはページ作成・更新も提供する。これを繋ぐと、
「read 専用の装備を支給する」ができない。設計は権限の段階的解放（§9.3）を掲げていて、
**新人にまず読み取りだけ渡す**のは思想の中心にある。向こうのツール一覧から write を
除外するフィルタを書くこともできるが、それは「持っていない」ではなく「使わせない」であり、
Prompt Guardrail Fallacy を構造に持ち込むのと同じ形になる（§9.2「未支給の装備はツール定義
自体をコンテキストに載せない」）。

副次的な理由として、装備1つのためにサブプロセスと別の認証経路が増える。
接続の失敗が「装備が使えない」ではなく「プロセスが立たない」として現れるのも扱いにくい。

### B. MCP を必須のまま、自前の MCP サーバーを書く

read 専用の MCP サーバーを自作すれば A の問題は消える。**採らなかったのは、
それが「HTTP クライアント + MCP のガワ」でしかないから**。同じコードに1層かぶせて
プロセス境界を足すだけで、得るものが「定義どおり」以外に無い。

将来 MCP 経由の装備（GitHub・ターミナル）を足すときは、その装備が MCP で繋げばよい。
**接続方式を装備ごとに選べる**というのが今回の決定の内容そのもの。

### C. 装備にせず、ただのツールとして register する

`ctx.tools.register("notion.search", …)` だけなら今日すぐ動く。**採らなかったのは、
装備台帳から外れるから**。誰にどの装備が支給されているかは可視性（§9.4）と
Policy Gate の allowlist の土台で、そこに載らない能力は「棚卸しできない権限」になる。
接続方式を緩めるのは構わないが、**管理下から外すのは緩めてはいけない方**。

## 結果

- 装備を1つ作るコストが下がった。外部サービスの読み取りは HTTP クライアント + 効果分類の申告で足りる
- 「read だけ支給する」が実際にできるようになった。`equipment-notion` は書き込みツールを持たない
- `mcpServer` という名前が実態と合わなくなった。いまは `{ kind: "http", baseUrl }` を入れている。
  MCP 経由の装備を実装するときに、`connection` のような中立な名前へ寄せるのが自然
- 装備ごとに接続方式が違う＝**共通化されたエラー処理が無い**。いまは各装備が
  `SourceResult`（§6.3）で結果を返す規約だけを共有している。装備が増えたら、
  リトライ・レート制限・タイムアウトの扱いを共通の層へ引き上げる必要が出る
