# 0007. 機微情報は記憶から落とさず、印を付けて公開経路で止める

- 状態: 採用
- 日付: 2026-08-11
- 関連: [`../preparation/governance/sensitive-info-guard.md`](../preparation/governance/sensitive-info-guard.md)、
  [`../preparation/governance/privacy-and-memory-policy.md`](../preparation/governance/privacy-and-memory-policy.md)、
  [`0003-model-decides-what-to-remember.md`](./0003-model-decides-what-to-remember.md)、
  [`0006-equipment-may-connect-without-mcp.md`](./0006-equipment-may-connect-without-mcp.md)

## 文脈

記憶は**全公開が前提**の設計だ（§10.1）。日記は毎朝 `#<個体名>-日報` へ投稿され、本棚は
読み取り専用 UI で閲覧できる。だから「日報に書いてよい／悪い」の線引き（DO-NOT-WRITE）が
仕様として定められている。

そこへ [ADR 0006](./0006-equipment-may-connect-without-mcp.md) で Notion を読む装備を足した。
疎通確認で最初に読めたページに、**未公開の予算額と実績値**が入っていた。
仕様が「書かない」と定めているもの（未公開の財務情報）そのものである。

（この ADR を含め、**実際の値はどこにも書かない**。実物を例示すると、ガードの説明そのものが
漏洩経路になる。以下の例はすべて架空の値。）

経路はこうなる。

```
Notion（限られた人が見る）→ メモ帳・本棚 → 日記 → #<個体名>-日報（全員が見る）
```

しかも何を記憶するかを決めるのはモデルで（[ADR 0003](./0003-model-decides-what-to-remember.md)）、
DO-NOT-WRITE のフィルタは**コードとして存在していなかった**（仕様の文章だけ）。

## 決定

**機微情報は記憶から落とさない。印を付けて残し、公開経路がその印を見て出さない。**

- 検出は**決定論的な純関数**（`inspectSensitive`）。仕様 §0 の「二次フィルタ」。
  返すのは**当たったカテゴリだけで、本文は含めない**（監査へそのまま載せられるように, A1-5）
- 記憶の書き込み口（`note.write` / `shelf.add`）で検査し、`sensitive_categories` に記録する
- **日記に載せない**。日記は毎朝投稿される＝ここが公開の境界。印の付いたメモは narrative から外す
- 昇格（メモ→本）では**材料のメモの印を引き継ぐ**。昇格を印の抜け道にしない
- 一次（生成プロンプト）にも DO-NOT-WRITE を入れる。二層にするのは仕様の要求（§0）で、
  プロンプトが効かなかったときに何も残らない状態を避けるため（Prompt Guardrail Fallacy, §9.2）
- 既定は仕様どおり **conservative / 全カテゴリ ON**。`AgentConfig.sensitiveGuard` で調節でき、
  形は `config_version.sensitive_guard` に合わせてある

## 検討した他の案

### A. 記憶に書かない（検出したら捨てる）

いちばん単純で、機微情報がデータベースに存在しなくなる。**採らなかったのは、それをやると
仕事に使えなくなるから**。マーケティングの相談相手に予算の数字を覚えさせないなら、
そもそも相談相手にならない。装備を足して外部文書を読めるようにした意味も消える。

**「知っているが言わない」は同僚として自然な振る舞い**でもある。人間の同僚は、聞いた給与の話を
忘れるのではなく、覚えたうえで日報に書かない。

### B. 公開の直前だけで検査する（仕様の字面）

仕様は「日記の生成時と投稿前」にガードを置いている。実装が公開経路だけで閉じるので変更も小さい。
**採らなかったのは、検出を最後の1箇所に集中させることになるから**。すり抜けたら即座に公開される。

印を書き込み口で付けておけば、公開経路（日記・日報・ビューア・将来の何か）は
**印を見るだけ**でよくなる。公開先が増えるたびに検出器を通す設計より、抜けにくい。

### C. モデルに判定させる（分類器）

人物評価（「Xさんは詰めが甘い」）は語彙では捕まえられないので、本当はモデルの判定が要る。
仕様の `filter_impl: "classifier"` はそれを想定している。**今回採らなかったのは、
決定論の層を先に置きたかったから**。分類器を最初に置くと、分類器が落ちたときに何も残らない。
順序として、決定論 → 分類器の追加、が正しい。

### D. Notion を読ませない（装備を回収する）

危険源を断つ案。**採らなかったのは、問題が Notion 固有ではないから**。同じ内容は Slack の
会話にも流れてくる（実際、機微情報は装備が無くても会話から入る）。装備を止めても経路は残る。

## 結果

- 記憶は仕事に使える状態のまま、公開経路には出なくなった
- 公開先が増えても、印を見るだけで済む
- **止まるものと止まらないものが非対称である。** 認証情報・金額・人事語彙のような
  語彙で決まるものはよく捕まえるが、**人物評価はほぼ捕まえられない**。
  `UNDETECTABLE_CATEGORIES` として明示し、すり抜けることをテストで固定した——
  「ガードを入れた」で人物評価も止まると誤解されるのが、いちばん危ない
- コーパステストが**検知漏れと過剰保留の両方**を数値で出す（現在 0/18・0/10）。
  片方だけ良くするのは簡単なので、両方を並べて出すことに意味がある
- **既定値とリストはサインオフ前**（決定オーナー: 人事 + 法務）。機構は入ったが、
  カテゴリの過不足と strictness の既定は承認待ちのままである
- 日報の投稿自体はまだ実装されていない。印は**投稿が実装される前に**入れられた——
  順序としてはこちらが正しい（後から入れると、それまでに溜まった記憶が一斉に公開される）
- 会話の返答は検査していない。同じチャンネルの相手に答えるのは「公開」ではないと整理したが、
  Slack のチャンネルは広さがまちまちなので、ここは将来の検討点として残る
