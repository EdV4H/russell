# 0008. 単語帳と個人カルテは索引カード（`entities`）に置く

## 文脈

2つの要望が出た。

- **単語帳** — チーム内でだけ通じる言葉（ユビキタス言語）の表
- **個人カルテ** — 人の情報。Slack の名前と普段の呼び名の対応など

どちらも「メモ帳・本棚で足りるのか、新しいテーブルが要るのか」が最初の問いだった。

設計書には既に `entities`（索引カード: `name` / `type` / `aliases` / `summary`）と
`entity_links` があり、**未実装のまま**だった。中心メタファーでも「本棚 **+ 索引カード**」で
1つの記憶と定義されている（[`12-memory-system.md`](../concepts/12-memory-system.md)）。

## 決定

**単語帳も個人カルテも `entities`（索引カード）に置く。`type` で分ける（`term` / `person`）。
新しいメタファーは足さない。**

- 想起は**別名の一致**で引く。`aliases TEXT[]` を構造で持ち、**モデルを使わずに照合する**
- 同じ語は**1件で更新**する（`(agent_id, type, lower(name))` に一意制約）
- 書き込みは記憶の判定（返答の後）で決める。**レイテンシは増えない**（ADR 0003）
- **段階的に入れる。** まず `term` だけ。`person` はガバナンスの制約とセットで後から
- 忘却曲線は**適用しない**。使わなくても定義や呼び名は忘れない

### 個人カルテの制約（2026-08-11 実装済み）

- 書いてよいのは**事実**だけ: 呼び名・所属・担当・何に詳しいか・連絡の好み
- 書かないのは評価・人物評（褒めるものも含む）・健康・人事・給与・対人トラブル
- **`type='person'` の summary は既定で日報に出さない**（[ADR 0007](./0007-sensitive-guard-marks-not-blocks.md) の印と同じ扱い）
- **取り直せるものは覚えない。** 表示名・アイコン・タイムゾーンは `users.info` で取れる
  （[ADR 0001](./0001-conversation-context-from-slack.md) と同じ判断）。覚えるのは
  「一緒に働いて分かったこと」だけ
- 退職者対応（`offboard_days`）の削除・匿名化の経路が要る。記憶は消さない方針だが、
  **人物データは privacy-and-memory-policy が明示的に例外にしている**。
  `pnpm --filter @edv4h/russell-worker forget-person -- "名前"` で消す。**個体には使わせない**
  ——「消して」と言われた個体が自分で消せる状態にしない（実行は承認者, §2）

## 検討した他の案

### A. 本棚（`books`）に置く

新しいテーブルが要らず、統合（[ADR 0004](./0004-shelf-organizing-is-reversible.md)）も
昇格（[ADR 0005](./0005-books-are-promoted-from-notes.md)）もそのまま使える。
**採らなかった理由は4つあり、どれも単独で十分だった**。

1. **忘却の意味が逆。** 本棚は毎晩減衰し、`strength < 0.2` で書庫へ落ちる。
   「1か月使わなかったので『MQL』の意味を忘れました」は事故である。本棚に置くなら、
   忘却曲線を個別に無効化する例外を作ることになる
2. **引き方が違う。** 本棚の想起は「直近5冊」。単語帳が要るのは**その語が文に出たとき**で、
   recency ではなく一致で引く
3. **一意であるべきものと、積み上がるもの。** 本は積み上がって夜に畳まれる（それが正しい）。
   一方「MQL」の定義は1つあって更新されるべきで、統合パイプラインに委ねると
   統合が失敗した夜は定義が2つある状態になる
4. **別名を構造で持てない。** `aliases` が要望の本体である。本文に「マルさんとも呼ばれる」と
   書くと**一致検索ができない**（部分文字列で誤爆する）

### B. 単語帳・個人カルテそれぞれに専用テーブルを作る

型が素直になる（用語に `strength` は要らない、人物に `definition` は要らない）。
**採らなかったのは、同じ構造の繰り返しになるから**。どちらも「名前・別名・要約」で、
違うのは `type` だけ。3つ目（プロジェクト・システム）が来るたびにテーブルが増える。
設計書が最初から `entities.type` にしていたのは、この予感があったからだと読んだ。

### C. メモ帳（`notes`）に置く

TTL があるので**7日で消える**。単語帳としては成立しない。

### D. エンティティ抽出をモデルにやらせる（設計書 §3.2 の想定）

設計書は「受信メッセージからエンティティ抽出（Haiku, ~200ms）」を想定している。
曖昧な言及（「あの人」「例の件」）まで拾えるのが利点。**今回採らなかったのは、
別名の照合だけならモデルが要らないから**。文字列一致なら**レイテンシを1ミリ秒も増やさない**——
返答前の経路に置くものは、増やさないに越したことはない（P0-1）。

曖昧な言及は拾えないが、それは最初から諦めてよい範囲だと判断した。必要になったら
D を**足す**ことはできる（照合を置き換える必要はない）。

> [!IMPORTANT] **補足（2026-08-12）: 表示名は覚えないが、「誰か」の紐付けは覚える。**
> `entities.external_ids`（`slack:U123`）に持つ。**表示名は取り直せるが、
> 「このカルテはこの Slack ユーザーのこと」という対応は Slack 側からは取れない**——
> こちらが持つべき情報。これがあると、表示名が変わっても同じ人だと分かり、
> 同じ人を別名で二重に持ったときに畳め、退職者対応を**名前ではなく id で**指定できる
> （同姓同名で誤爆しない）。
>
> 紐付けは**和集合で足すだけ**で、外すのは人の操作。名前の揺れ（「丸山」/「丸山さん」）は
> 包含関係で吸収するが、**2文字未満は当てにいかない**（短い名前は誤爆する）。

> [!IMPORTANT] **補足（2026-08-12）: 同じ名前で書くと、内容は丸ごと置き換わる。**
> 別名と紐付けは和集合で足すが、**要約は上書き**である（`SET summary = EXCLUDED.summary`）。
> 一方で判定に見せていたのは**見出し語と別名だけで、本文は渡していなかった**——
> 「上書きではなく、分かったことを足す形で書く」と指示しておきながら、
> **足す先が見えていなかった**（守りようがない）。同じ語が2回目に出るたびに、
> それまでに分かっていたことが今日の1行で消えていた。
>
> **その会話に出てきた語・人**の現在の内容を判定へ渡す（一致で引くので全件は渡らない）。
> そのうえで「同じ name で出すと丸ごと置き換わるので、全文を書き直せ」と明示する。
> 統合はモデルが行う（[ADR 0003](./0003-model-decides-what-to-remember.md) の路線）——
> DB 側で追記にすると、同じことが何度も積まれて誰も読まないカードになる。
>
> **上書きであることは変えていない。** 消えた記述を後から復元する経路は無いので、
> 履歴が要ると判断したら `entity_revisions` を別途決める。

## 結果

- 単語帳が動く。意味が説明された語を覚え、次にその語（や別名）が出たときに文脈へ入る
- **メタファーが増えなかった。** 「本棚 + 索引カード」の定義のままで説明できる
- 個人カルテも動いている（2026-08-11）。**先に「何を書かないか」を決めてから器を作った**順序は
  正しかった——判定プロンプトの制約がそのまま実装の中心になり、器の側は用語と同じ仕組みで済んだ
- 誤爆の危険は残る。1文字の別名は照合に使わない（**誤爆した用語を注入するのは、何も注入しない
  より悪い**——関係ない定義を前提に答え始める）が、2文字の略称が別の語の一部に当たることはありうる
- `entity_links`（本・メモとの結びつけ）は未実装。「この用語について何を知っているか」を
  辿れるようにするのは次の段階
- 単語帳は `agent_id` 単位。ユビキタス言語は本来チームの資産なので、2体目が出たときに
  「共有するのか、個体ごとに覚え直すのか」を決め直す必要がある
