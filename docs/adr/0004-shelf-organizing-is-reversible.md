# 0004. 本棚の整理は夜間バッチで行い、可逆にする

- 状態: 採用
- 日付: 2026-08-11
- 関連: [`0003-model-decides-what-to-remember.md`](./0003-model-decides-what-to-remember.md)、
  [`../concepts/17-habits-and-sleep.md`](../concepts/17-habits-and-sleep.md)、
  [`../preparation/governance/privacy-and-memory-policy.md`](../preparation/governance/privacy-and-memory-policy.md)

## 文脈

記憶するかどうかをモデルが決めるようになって（[ADR 0003](./0003-model-decides-what-to-remember.md)）、
**会話が続くほど似た本が積み上がる**ようになった。オンボーディング1回・3ターンで本が2冊でき、
2冊目が1冊目をほぼ包含していた。

本棚は「眺めて引く」ための索引なので、重複はそのまま索引の劣化になる。さらに見出しが
本文の先頭24文字の切り出しだったため（[#49](https://github.com/EdV4H/russell/pull/49) で修正）、
既にある本は見出しからは何の話か分からない状態だった。

放っておくと、想起（`recall` は直近5冊）が重複で埋まり、古い本が押し出される。

## 決定

**本棚の整理は夜間コンソリデーションの一部（§4-3「本棚の編集」）として行い、操作はすべて可逆にする。**

- 何をまとめるかは**モデルが決める**（ADR 0003 と同じ理由。重複判定は自然言語の意味の問題）
- 畳まれた本は**消さずに `archived`**（書庫へ下げる = privacy-and-memory-policy §3 の L1）
- **残す側の元の文章も、上書き前に書庫へ控える。** これが無いと、畳まれた側は後から読めるのに
  残した側の元文だけが消え、整理が部分的に不可逆になる
- モデルが返した id は信用せず、**実在する・自分の・active な本だけに絞ってから適用**する（§12-3）。
  untrusted なテキストを読んだモデルの出力で DB を書き換える経路だから
- 読めない出力は「何もしない」に倒す。整理は急ぎではない
- 適用は1トランザクション。畳まれた側だけ書庫に落ちて残す側が更新されない状態を作らない
- `--dry-run` は**何も書き込まない**（日記も忘却も含む）。数字は「やったらどうなるか」を返す
- 整理は監査に残す（`memory.shelf.organized`）。**payload は id と件数だけ**（A1-5）

**メモ帳（`notes`）は整理しない。** 理由は下記。

## 検討した他の案

### A. 書き込む前に重複を判定する（本を足す時点でまとめる）

重複が最初から生まれないので、いちばん筋がよく見える。**採らなかったのは、返答のレイテンシに
乗るから**。既存の本を全部読んで比較する処理をターンの中に入れると、ADR 0003 で判定を
ターンの後ろに置いた理由（P0-1: p95 ≤ 8s）をそのまま壊す。設計も「重い LLM 処理はすべて
夜間へ寄せる」と決めている（§4）。

さらに、書く時点では重複かどうか判断しきれない。3冊目が来て初めて「この2冊は同じ話だった」と
分かることがある。**まとめる判断は溜まってからの方が正確**で、これは人間の記憶の固定化が
睡眠中に起きるのと同じ形をしている。

### B. 埋め込みベクトルの類似度でまとめる

`books.embedding vector(1024)` は既にスキーマにある。閾値を超えた組を機械的にまとめれば
モデル呼び出しが要らない。しかし:

- P0 では埋め込みを入れていない（recall は recency ベース）。この案のためだけに埋め込み経路を
  先に作ることになる
- 類似度が高い＝まとめてよい、ではない。「定例は金曜15時」と「定例は木曜15時」は
  ベクトル的には近いが、**まとめると事実が壊れる**。閾値では捉えられない
- まとめた後の本文（両方の具体を落とさずに1〜3文）は、結局モデルにしか書けない

### C. 物理削除でまとめる（畳まれた本を DELETE する）

本棚がすっきりし、書庫が膨らまない。**採らなかったのは、サインオフ前に不可逆な操作を
既定にできないから**（privacy-and-memory-policy §2）。L2（物理削除）は HITL 承認が前提で、
その HITL 自体がまだ無い。整理はエージェント自身が夜中に走らせる処理なので、
**人が見ていないところで不可逆な操作をする**形になるのはなおさら避けたい。

### D. 人が承認してから適用する（HITL）

安全側に倒すならこれ。ただし毎晩の整理に承認を挟むと運用が回らない。可逆にしたうえで
**監査に残し、`--dry-run` で事前に見られる**ようにする方を選んだ。不可逆な操作（L2）を
入れるときは、そのとき HITL を要件にする。

### E. メモ帳も整理する（期限切れのメモを削除する）

`notes_ttl_days: 7` があり、期限切れのメモは想起から外れるが**行としては残り続ける**ので、
これも整理の対象に見える。採らなかったのは C と同じ理由——保持期間の既定値は
まだサインオフされておらず（§2）、L2 が未実装だから。**期限切れは削除の理由にならない**。

メモには既に別の畳み方がある（夜間バッチが日記へ畳んで `consolidated` を立てる）ので、
放置されているわけでもない。溜まった行の物理削除は、retention のサインオフと合わせて扱う。

## 結果

- 本棚が索引として使える状態を保てる。重複が増えても夜ごとに畳まれる
- 整理の結果に不満があっても戻せる。**すべての元の文章が書庫にある**
- 代償として書庫が膨らむ。1回の統合で「畳まれた本」＋「残す本の控え」が積まれる。
  `archived_hard_delete_days`（既定案24か月）のサインオフが済むまで、書庫は増える一方
- 夜間バッチがモデルを呼ぶようになった。worker はこれまでモデルを持たず、コアの外にいたため
  `createClaudeCodeProvider` を切り出した。監査も worker から書けるように `appendAuditEvent` を足した
  （worker には AuditRegistry が無い。それでも「全アクションが残る」は満たす必要がある）
- **まとめ方の質はモデルの出力に依存する。** 「迷ったらまとめない」と指示してあるが、
  別の話題を1冊にしてしまう失敗は起こりうる。起きた場合に気づける仕掛け（本棚ビューアと監査）は
  あるが、自動では検出できない
