# 0002. 会話の文脈は記憶ではない（通信面の関心事）

- 状態: 採用
- 日付: 2026-08-10
- 関連: [`0001-conversation-context-from-slack.md`](./0001-conversation-context-from-slack.md)、
  [`../concepts/12-memory-system.md`](../concepts/12-memory-system.md)、
  [`../concepts/13-surfaces.md`](../concepts/13-surfaces.md)

## 文脈

会話を成立させるため、文脈ごとに直近のやりとりを保持する層を足した。これを実装上
`workingMemory` と命名したが、記憶システムの4つのメタファーでは
**メモ帳＝ワーキングメモリ**と定義されている（[`12-memory-system.md`](../concepts/12-memory-system.md)）。
同じ名前で別のものを指す状態になり、「メモ帳と何が違うのか」が説明できなくなった。

さらに、この層の単位（Slack のスレッド）は**通信面が決める概念**であって、
記憶システムの語彙ではない。記憶の体系にスレッドを持ち込むと、Slack の都合が
記憶の設計に染み出す。

## 決定

**会話の文脈は記憶ではない。通信面の関心事として、記憶システムから切り離す。**

- 記憶システムの4つのメタファー（メモ帳・日記・本棚・書庫）に**5つ目を足さない**
- 単位は `contextId` で、それが何を指すかは通信面が決める
  （Slack はスレッド、DM はチャンネル、CLI はセッション）。コアは中身を解釈しない
- 実装の名前から「記憶」を外す（`workingMemory` → `conversationContext`）

境界の言い方: 記憶システムは Bob が「**保つ**」ものの体系。会話の文脈は「**いま抱えている**」もの。

## 検討した他の案

### A. 5つ目の記憶メタファーとして体系に加える

最初に考えた案。**採らなかったのは、体系が壊れるから**。4つのメタファーは
「認知科学上の記憶の種類 × 人間が使う道具」という一貫した軸で選ばれている。
そこへ「Slack のスレッド単位で保持されるバッファ」を並べると、軸が
道具でも記憶の種類でもなくなる。中心メタファーは説明のための構造なので、
説明できなくなった時点で価値を失う。

### B. メモ帳（`notes`）に統合する

概念が1つで済み、永続化と TTL も既にある。しかし:

- メモ帳は夜間バッチで日記に畳まれる。会話の全発言を流すと**日記が「今日言われた全部」になる**
- 本文を DB に溜めることになり、[ADR 0001](./0001-conversation-context-from-slack.md) で
  避けた保持の問題が戻ってくる
- そもそも意味が違う。メモ帳は「書き留めたものだけが残る」記憶で、10秒前の発言を
  メモに取る人はいない

## 結果

- 記憶システムの語彙が保たれる。「メモ帳＝ワーキングメモリ」の定義を変えずに済む
- 通信面を差し替えても記憶の設計が動かない。Slack のスレッドという概念が記憶側に漏れない
- 会話の文脈は**永続化しない**方針（ADR 0001）と整合する。記憶ではないので、
  記憶の保持ポリシー（TTL・削除依頼・全公開）の対象にもならない
- 代償として、層が1つ増える。「Bob は何を覚えているのか」を説明するとき、
  記憶（4つ）と会話の文脈を分けて話す必要がある
