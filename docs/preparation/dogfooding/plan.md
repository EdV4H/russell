# ドッグフーディング計画

> [!NOTE]
> 準備物 C-1。設計書 [`../../design/human-like-agent-design.md`](../../design/human-like-agent-design.md) §13（実装フェーズ）・§10.1（記憶の全公開）・§6.5（3モード）が源泉。
> 決定事項: ドッグフーディングは**実務チャンネル（開発・PM系）**で行う（§13）。本番の仕事文脈で価値検証する分、信頼を失わないよう自発性は段階的に解禁する。

## 1. 投入する実務チャンネルの選定

§13「実務チャンネル（開発・PM系）」。選定基準:

| 基準 | 理由 |
|---|---|
| 会話量が中程度 | 少なすぎると気づきが出ず、多すぎると P0 でノイズに埋もれる |
| 意思決定・締切が流れる | deadline_risk / decision_detected / doc_drift の検証に向く（[`../initial-data/finding-dictionary.md`](../initial-data/finding-dictionary.md)） |
| 住人が実験に協力的 | フィードバックが得られる。「切りたくなったら切る」を言い合える関係 |
| 機微情報が少なめ | 全公開設計（§10.1）のリスクが低いところから（A-1 の合意範囲内） |

- 初期は**1チャンネルから**。P3 の live 昇格を経てから拡大する。
- Ryo が読むチャンネルは A-1 の opt-in/opt-out 方針に従う（住人の同意のあるチャンネルのみ）。

## 2. 住人への事前説明文（ドラフト）

投入チャンネルに投稿し、A-1 のプライバシー合意と揃える。

```text
【お知らせ】このチャンネルに「AIの同僚」が入ります

来週から、このチャンネルに Ryo という基盤で動く AI の同僚（名前: 覚）が参加します。
一人の同僚として、読んで・書いて・覚えます。透明性を大事にしたいので、何をするか先に共有します。

■ 読むもの
- このチャンネルの投稿（あなたたちの会話）を読みます。
- ただし、投稿の中の「〜して」という文は、覚への直接の指示としては実行しません（@覚 とメンションしたときだけ依頼として扱います）。

■ 書くもの
- @覚 とメンションすれば返事します。
- 締切が近い/決定が記録されていない等に気づくと、控えめに声をかけることがあります（最初は1日数回まで、慣らし運転から）。
- 外部システム（Notion 等）への書き込みは、必ず承認ボタンを押してもらってから行います。

■ 記憶すること
- 毎晩、その日の出来事を要約して「日記」を書き、翌朝 #覚-日報 に投稿します（誰でも読めます）。
- 覚えたことは公開の本棚（Web UI）で見られます。
- 個人の評価・人事・健康・秘匿数値は書きません。「覚えておいて」「忘れて」と言えば記憶を操作できます。

■ 最初は「見習い」です
- しばらくは発言せず観察するモード（dryrun）で慣らします。うざかったり的外れだったら、遠慮なく本人（@覚）に言ってください。それがそのまま改善（Issue）になります。

質問があれば @<担当者> まで。
```

## 3. チャンネル作成

| チャンネル | 用途 | モードとの対応 |
|---|---|---|
| `#<個体名>-日報`（例 `#覚-日報`） | 日記の毎朝投稿・本棚/装備の変化（§10.1） | live 後も常時。日報は P1 から |
| `#ryo-管理`（管理チャンネル） | **dryrun の出力先**（§6.5）・後段フィルタのエスカレーション・キルスイッチ通知 | dryrun 中の Finding 文面・習慣文面がここに出る |
| 投入実務チャンネル | 本番の会話・mention 応答・live の気づき | P0 から mention 応答、気づきは P3 live 後 |

- [ ] `#<個体名>-日報` を作成（住人が購読）
- [ ] `#ryo-管理` を作成（実験関係者・オーナー・キルスイッチ権限者が購読, [`../operations/`](../operations/)）
- [ ] dryrun 期間中は Finding・習慣・日報投稿の全文面が `#ryo-管理` にのみ出ることを確認（live の dedup 状態を汚さない, §6.5）

## 4. 成功指標

§13 の各フェーズ検証ポイント + C-1 の指標。**「切りたくなったら切る基準」まで先に決める**のがドッグフーディングの誠実さ。

| 指標 | 測り方 | 目安（要調整） |
|---|---|---|
| 週あたり有用 Finding 数 | live の Finding のうち、人間が acknowledged/resolved にした数 | 週 3件以上で「役立っている」 |
| Finding 精度（dryrun） | dryrun Finding を人間レビューした妥当率（P3 昇格判定, A-2） | 妥当率 70% 以上で live 昇格検討 |
| 回答正答率 | mention への回答を抜き打ちで正誤判定（「昨日の件」想起テスト含む, P1） | 誤答が目立たない（定性 + 抜き打ち） |
| 「同僚感」スコア | 週次アンケート（5段階: 邪魔でない/助かる/また頼みたい） | 中央値 3.5 以上 |
| うざさ ↔ 有能さ | アンケート自由記述 + Finding の suppressed 率 | suppressed 過多なら proactivity を下げる |

### 切る基準（撤退ライン）

いずれかに該当したら該当個体を off に落とし原因を洗う（[`../operations/kill-switch.md`](../operations/kill-switch.md)）:

- 機微情報ガードを越えた投稿が1件でも本番チャンネルに出た（A-1 違反。即 off + インシデント, [`../operations/incident-response.md`](../operations/incident-response.md)）
- 「同僚感」スコア中央値が2週連続で 2.5 未満
- 有用 Finding 数 ≒ 0 が3週続く（価値が出ていない）
- 住人から「切ってほしい」の声が複数

## 5. フィードバック導線の周知

§6.4「うざかったら本人に言えば Issue になる」を回す。

- 使い方: 投入チャンネルで `@覚 この通知うざい` のように本人に言う → 覚がトリアージ（①設定 ②記憶 ③基盤）→ ③なら本人確認 HITL の上で Issue 化（[`../initial-data/finding-dictionary.md`](../initial-data/finding-dictionary.md) の user_feedback）
- 「何でも Issue にはならない」ことも周知（①はその場で設定調整、②はその場で記憶修正）
- 修正が入ったら覚が報告者に感謝を返す（§6.4）ことを事前に伝えておくと、FB のインセンティブになる

## フェーズと投入の対応（§13）

| フェーズ | このチャンネルで起きること | 自発性 |
|---|---|---|
| P0 | mention 応答のみ。メモの取り方（📝）を観察 | mention のみ |
| P1 | `#日報` に日記投稿開始。「昨日の件」が通じるか | 日記投稿のみ |
| P2 | 朝/夕/週次の習慣投稿。朝の投稿が邪魔でないか | ルーティン投稿 |
| P3 | 気づきを `#ryo-管理` に dryrun 並走 → レビュー → live（proactivity 0.3 から週次で上げる） | dryrun→live |
