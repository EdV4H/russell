## 0. なぜこの合意が発注前ブロッカーなのか

Ryo は同僚の Slack 発言を記憶（メモ帳・本棚・日記）に貯め、しかも **記憶を全公開する**（設計書 §10.1「記憶の全公開（決定事項）」）。日記は毎朝 `#<個体名>-日報` チャンネルへ投稿され、本棚は読み取り専用 Web UI で誰でも閲覧できる。つまり「誰が・いつ・何を言ったか」を要約したものが、本人以外の目に触れ続ける。

これは技術的な良し悪しではなく、労務・プライバシーの問題である。Frank v2 の運用知見でも「**Phase 1 から PII 複製が始まる前に retention を定めよ**」とされている。実装が始まって PII のコピーが DB に溜まり始めてからでは、遡って方針を当てはめるのが困難になる。**本ドキュメントの各 `[!TODO]` が埋まるまで、記憶を永続化するフェーズ（P1 以降）の実装に着手させない。**

> [!TODO]
> **本方針全体の最終承認者（人事・法務）を確定する。** 全公開という前提そのものが労務上許容されるか、限定公開に変更が必要か（チェックリスト優先順位「結論次第で設計が変わる（全公開→限定公開になる可能性）」）を含めて、人事責任者・法務担当の署名をもって発注ブロッカーを解除する。承認日・承認者名をここに記録すること。

## 1. 従業員データの記憶・要約・日報公開の労務／プライバシー確認

### 提案デフォルト（ドラフト）

- Ryo が投入されるチャンネルの参加者全員に、投入前に周知する（何を読み・何を書き・何を記憶するか）。周知文面はドッグフーディング設計（[`../dogfooding/plan.md`](../dogfooding/plan.md)）と共通化する。
- 記憶・日報公開の対象は **業務上の発言のみ**。DM（`message.im`）はメモ帳の短期文脈としては使うが、日記・本棚への昇格対象からは除外する（本人との1対1のやり取りを公開日報に出さない）。
- 日報・本棚に載る記述は「出来事・決定・学び」に限定し、個人の評価・人物評は載せない（具体の線引きは [`sensitive-info-guard.md`](./sensitive-info-guard.md)）。

### チェックリスト

- [ ] Slack 発言を記憶・要約・日報公開することの労務観点確認（人事）
- [ ] 同・プライバシー／個人情報保護観点の確認（法務）
- [ ] 就業規則・プライバシーポリシー・従業員向け同意文の改定要否の判断
- [ ] DM を記憶対象に含めるか否かの確定（デフォルト提案: 短期文脈のみ可・永続化不可）
- [ ] 投入チャンネル参加者への周知文面の承認

## 2. Retention（保持期間・削除依頼対応手順）

### 提案デフォルト（ドラフト）

設計書のデータモデル（§3.1）と忘却曲線（§3.4）を踏まえた叩き台:

| データ | 提案保持期間 | 根拠 |
|---|---|---|
| メモ帳 `notes` | 既定 7 日（`expires_at`）で失効 | §3.1 で既定 7 日と定義済み |
| 日記 `journal_entries` | 提案: 13 か月（前年同月比較を1回できる範囲） | 明示定義なし。要決定 |
| 本棚 `books`（active） | 減衰で `strength < 0.2` → `archived`（書庫へ、削除しない） | §3.4。物理削除の期限は未定義 |
| 本棚 `books`（archived / 書庫） | 提案: 24 か月で物理削除 | 「書庫は削除しない」は無期限保持を意味するため要判断 |
| 監査ログ `event_log` | 提案: 削除しない（追記専用・法定保存的扱い） | §3.1「全アクション追記専用」 |
| 使用量イベント台帳 | 提案: 24 か月 | コスト分析用途 |

- **退職者の扱い（提案）**: 退職者本人の発言由来の記憶は、退職から N 日以内に削除または匿名化する。N は要決定。
- **削除依頼の受付窓口（提案）**: Slack の管理チャンネル or 指定フォーム経由で受け付け、承認者（[`../operations/`](../operations/) の運用体制で定める）が実行。実行は `config_version` と event_log に記録する。

### チェックリスト

- [ ] 各データ種別の保持期間の確定（上表を埋める）
- [ ] 退職者データの削除・匿名化ポリシーと期限 N の確定
- [ ] 削除依頼の受付窓口・本人確認方法・SLA（何営業日以内）の確定
- [ ] 書庫（archived）の物理削除期限の確定（無期限保持の是非）
- [ ] バックアップ（別環境の不変保存、§12-6）に対する削除の反映方法（不変保存と削除権の両立をどうするか）

## 3. 「忘れて」と言われたときの削除範囲

### 論点

設計書 §10 で「覚えておいて」「忘れて」を自然言語コマンドとして解釈するとある。「忘れて」が **どこまで消すか** は設計上あいまいで、削除の実体は §3.3/§3.4 の strength 操作および status（active / archived）で表現される。選択肢は大きく次の3段階:

| レベル | 実体 | 効果 |
|---|---|---|
| L1: 弱める | 対象 book の `strength` を下限まで下げる → 書庫落ち（`archived`） | 会話の想起パスから外れるが、データは残る・`deep_recall` で到達しうる |
| L2: 本棚から削除 | 対象 book を物理削除。索引カード・entity_links も更新 | 本棚からは消える。日記の該当記述は残る |
| L3: 遡及消去 | L2 に加え、日記 `journal_entries` の該当イベント記述も編集／削除 | 日記チャンネルの過去投稿との不整合が発生しうる |

### 提案デフォルト（ドラフト）

- 通常の「忘れて」= **L1（弱める）**。設計書の忘却曲線の思想（「削除はしない」§3.4）に最も忠実で、可逆。本人へ「本棚から下げて、普段は思い出さないようにしました」と返す。
- 明示的に「完全に消して」と言われた場合 = **L2**。実行前に HITL 確認（内容プレビュー + 承認ボタン）。
- **L3（日記の遡及消去）は既定では行わない。** 日記は夜間バッチが書く来歴付きの監査対象（§12-5）であり、遡及編集は監査可能性を損なう。L3 が必要なのは §2 の正式な削除依頼手続き経由のみとする。

### チェックリスト

- [ ] 「忘れて」の既定レベル（L1 / L2 / L3）の確定
- [ ] L2/L3 実行時の HITL 確認フローの確定
- [ ] 日記の遡及消去を認めるか、認める場合の監査ログの残し方
- [ ] 既に日報チャンネルへ投稿済みの過去メッセージの扱い（Slack 上の投稿も消すか）

## 4. 参加チャンネルの opt-in / opt-out 方針

### 提案デフォルト（ドラフト）

- **opt-in を既定とする。** Ryo は明示的に招待され、かつ管理者が台帳に登録したチャンネルのみ購読・記憶する（§10 の購読は `app_mention` / `message.im` / 参加チャンネルの `message.channels`）。「いるチャンネル全部を勝手に読む」は既定で禁止。
- チャンネル追加は管理者操作（`/ryo config` 相当、§6.1 の管理者コマンド）で行い、event_log に記録する。
- **機微チャンネルのブロックリスト**: 人事・給与・health・1on1・経営など、招待されても記憶しないチャンネル種別を定義する（[`sensitive-info-guard.md`](./sensitive-info-guard.md) と連動）。
- チャンネル参加者が「このチャンネルでは記憶しないで」と opt-out できる導線（管理者への申請）を用意する。

### チェックリスト

- [ ] opt-in 既定の承認（勝手読みの禁止）
- [ ] チャンネル追加の承認者・手続きの確定
- [ ] 記憶禁止チャンネル（ブロックリスト）の初期リスト作成（[`sensitive-info-guard.md`](./sensitive-info-guard.md) と共有）
- [ ] opt-out 申請の受付導線の確定
