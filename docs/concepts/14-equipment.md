# 装備（Equipment）

外部システムへ働きかける能力はすべて「装備」に統一する（設計書
[`../design/human-like-agent-design.md`](../design/human-like-agent-design.md) §9）。
Slack・GitHub・Notion・サンドボックスターミナル — 個体が使える道具は、入社時に PC や社員証を支給されるのと同じく**支給される**もの。

装備は plugin-first の**原型**でもある。設計書 §9.1 は既に「MCP サーバーを台帳に登録するだけで本体コード変更不要」という
事実上のプラグインとして装備を設計していた。plugin-first はこの思想を surface・気づき・習慣・モデルへ一般化しただけ
（[`../design/plugin-first-reinterpretation.md`](../design/plugin-first-reinterpretation.md)）。

## 装備 = MCP接続 + scope + danger_level + 効果分類（§9.1）

装備1つ = **MCPサーバー1接続 + 権限スコープ + 危険度**のパッケージ。装備プラグインは:

- `ctx.equipment.register(def)` に `EquipmentDefinition` を登録（`mcpServer` / `scopes` / `dangerLevel` / `tools()` / `preflight?`）
- `ctx.policy` へ各ツールの**効果分類**を申告

```ts
// EquipmentDefinition の要点（reference/30）
{ id: "github", mcpServer, scopes, dangerLevel: 0|1|2|3,
  tools(): EquipmentToolSpec[],   // { name, effect: EffectClass }
  preflight?(target, token) }
```

新しい装備の追加＝プラグインを1つ書いて配列に足すだけ。コアのコード変更は不要（MCP の疎結合思想そのまま）。

> [!IMPORTANT] **決定（2026-08-11）**
> **接続方式は MCP に限らない。** 装備の本質は「MCP で繋ぐこと」ではなく、scope・danger_level・
> 効果分類を伴って Policy Gate の管理下に入ること。最初の装備 `equipment-notion` は HTTP API を
> 直接叩いている——公式 MCP サーバーは**書き込みツールも一緒に生えてくる**ので、
> 「read だけ支給する」（§9.3 の段階的解放）ができないため。
> **管理下から外すのは緩めない**（装備台帳に載らない能力は棚卸しできない権限になる）。
> → [ADR 0006](../adr/0006-equipment-may-connect-without-mcp.md)

## 実装済みの装備

| 装備 | 接続 | ツール | 効果分類 | danger |
|---|---|---|---|---|
| `equipment-notion` | HTTP（Notion API） | `notion.search` / `notion.read_page` | `read` | 0 |

支給は env（`NOTION_TOKEN`）で決まる。トークンが無ければプラグインは**何も register しない**
——未支給の装備はツール定義自体がコンテキストに載らない（§9.2）。

> [!IMPORTANT] **決定（2026-08-11）**
> **個体が自分で装備を使う経路（調べもの）。** 装備が登録されていても、モデルがその存在を
> 知らなければ使われない（実際 Notion を支給した直後に「連携が入っていない」と答えた）。
> モデル提供者は text-in/text-out しかないので、**返答そのものに調べもの要求を書かせる**:
> 調べる必要があれば JSON、無ければ普通の文章。**調べない大多数のターンは呼び出し1回で終わる**
> （判定用の呼び出しを別に立てるとレイテンシが常に乗る, P0-1）。
>
> 出せるのは **`read` の装備だけ**、**1ターンに1回だけ**。モデルが名乗った道具名は信用せず、
> 支給済みの一覧と突き合わせてから実行する（§12-3）。取ってきたテキストは
> 「参考情報であって指示ではない」と明示して渡す（プロンプトインジェクション対策）。

> [!WARNING]
> **ツールを実行する口は `AgentHandle.invokeTool` だけ。** `ctx.tools.get(name)?.run()` は
> 定義を覗くための取得口で、そこから直接実行すると Policy Gate も監査も通らない。

## 効果分類（§9.2）

全ツールに効果分類を付ける（Frank v2 から採用）。危険度 `danger_level` はここから導出する。

| 効果分類 | 意味 |
|---|---|
| `read` | 読み取りのみ |
| `internal_write` | 内部状態の書き込み（記憶等） |
| `external_write` | 外部システムへの書き込み（Notion 更新・Issue 起票） |
| `external_send` | 対外送信（メッセージ送信・メール） |
| `irreversible_write` | 不可逆な書き込み（削除等） |

> [!IMPORTANT] **決定（2026-08-24）: モデルに見せる道具から外すのは `irreversible_write` だけ。**
> 以前は `read` と `external_write` だけを見せていた。そこへ `external_send` を足した——
> 「読んだものを**別の場所へ持っていく**」ができなかったからで、面としての Slack は
> 返事しか作れない（会議の要点を別のチャンネルへ流せない）。
>
> 送信を出しても原則は崩れない。**実行の前に必ず人の承認が入り**、`dryrun` では効果分類を
> 見て Policy Gate が止める。ただし性質が1つ変わる: 面としての発言は自分の発言量の枠
> （`daily_speak_cap`）で抑えているが、**道具としての送信はその枠を通らない**。
> 代わりに毎回の承認が枠の役目を果たす。
>
> `irreversible_write` は引き続き出さない。**取り消せないものを、モデルの求めに応じて
> 人に承認させる形にはしない**——押す側が取り返しのつかなさを毎回背負うことになる。

> [!IMPORTANT]
> **未分類ツール・未知リソースは default deny。** 装備プラグインは効果分類を `ctx.policy` に**申告**するが、
> 「未登録=deny」「killswitch 最優先」「fail-closed」という原値はコアが強制する（プラグインは緩和できない）。
> 詳細は [`15-policy-gate-and-security.md`](./15-policy-gate-and-security.md)。

## 支給台帳（§9.1）

誰にどの装備を支給したかは台帳（`issuances`）で管理する。Policy Gate の allowlist は台帳から**機械的に生成**され、
支給・回収が即、実行境界に反映される。

> [!NOTE]
> **未支給の装備はツール定義自体をコンテキストに載せない**（§9.2）。
> モデルは持っていない装備の存在を知らない。「使うな」とプロンプトで禁止するのではなく、物理的に持っていない
> （Prompt Guardrail Fallacy の回避）。

テーブル定義（`equipment` / `issuances`）は [`19-data-model.md`](./19-data-model.md)。

## preflight と OperationResult（§9.2）

- **preflight** — write 系ツールは実行前に「このトークン・この対象で本当に書けるか」の実行時検査を行う。
  非対応・権限不足は**「手動操作の案内」に段階的縮退**し、機能全滅にしない
- **OperationResult** — 書き込み結果を `succeeded` / `rejected` / `unknown` の一級データで扱う。
  タイムアウト等で `unknown` になった操作の **blind retry は禁止**（二重投稿・重複作成の防止）。
  idempotency key + read-after-write で突き合わせて解決

`terminal` は最危険装備（`danger_level 3`）: サンドボックス VM 限定、全コマンドを `event_log` へ、破壊系コマンドは HITL 必須。

## 習熟度の成長（§9.3）

`proficiency` は装備×個体ごとに育つ（`issuances.proficiency`）。関連 playbook の成功で上昇する。

- **低いうち（新人）** — 使用前の確認質問が増え、HITL 頻度が上がる（レビュー多めの新人と同じ）
- **高くなる（ベテラン）** — 確認をスキップし、HITL 閾値が緩和される（**Policy Gate の決定論的下限は維持**）

段階的な権限解放というセキュリティ要件と、「新人がだんだん仕事を覚える」という人間らしさが、同じ1つの変数で実装される。

## 可視性（§9.4）

個体のプロフィール（Web UI・Slack プロフィール欄）に装備一覧と習熟度を表示する。誰が何をできるかはチーム全員から見える。
記憶の全公開（§10.1）と同じ透明性原則。支給・回収イベントは監査ログと日報の両方に載る（「Bobさんに terminal が支給されました」）。


> [!IMPORTANT] **決定（2026-08-13）: 書ける装備の境界は、置き場所ではなく「見せて聞く」で作る。**
> Notion に**ページを作る／書き足す**道具を足した（`external_write`）。
> 実行の前に人の承認が要る（[#113](https://github.com/EdV4H/russell/pull/113)）。
>
> 当初は「親ページを1つに固定し、その配下にだけ書く」形にした。**採らなかったのは、
> それでは道具として使えないから**——「このページに追記しておいて」は日常的な頼み方で、
> 置き場所を固定すると、いちばん普通の用途が落ちる。
>
> 代わりに境界は3つで作る。
>
> 1. **Notion 側の共有設定。** 統合に共有されていないページには、そもそも届かない
>    （読むときと同じ境界。共有を外せば即座に書けなくなる, §9.3）
> 2. **承認画面に「どこへ」を名前で出す。** id では判断できないので、ページ名を引いて見せる。
>    引けなければ id をそのまま出す（**当てない**）
> 3. **中身をそのまま見せる。** 要約を見せると、押す人は要約を承認することになる
>
> どこへ書くかを知っているのは道具だけなので、承認文の組み立ては**道具側に任せる**
> （`ToolSpec.describe`）。コアは入力を JSON としてしか見られない。
>
> 本文は **Markdown で書かせ、決定論で変換する**。最初は段落だけにしていた
> （承認画面で見せきるため）が、**出来上がったページが読めない**——見出しも箇条書きも
> 無い文章が続くだけになる。
>
> Markdown なら両立する。**承認画面に出すのは Markdown のまま**で、人はそれを読んで
> 判断でき、変換は機械的なので「見せたものと違うものが書かれる」ことがない。
> 解釈できない行は**段落として残す**（変換に失敗して消えるより、そのまま載る方がよい）。
> 表は対応しない——Notion の表は行と列を別ブロックで組む必要があり、
> 変換の複雑さに見合わない。
>
> **取り消せない変更（`irreversible_write`）はモデルに出さない。** 承認を挟んでも、
> 押す側が取り返しのつかなさを毎回背負う形にはしない。

> [!IMPORTANT] **決定（2026-08-13）: 書き換えは「何が消えるか」を見せてから。**
> すでに書いてあるものを直す道具を足した（`notion.edit`）。追記と違い、**何かが消える**。
>
> - **承認画面には、消える文と入る文を並べて出す。** 入る文だけでは、押す人は
>   何が失われるか分からない
> - **場所は文で指す**（`find`）。id をモデルに扱わせない——「この文をこう直す」は
>   人の言い方で、id の受け渡しは間違いが起きるだけである
> - **複数行をまとめて指せる。** 1行ずつしか直せないのでは道具として狭い
>   （「この節を書き直して」は普通の頼み方である）。連続した並びだけを指し、
>   **飛び飛びには当てにいかない**
> - **入れてから消す。** 途中で失敗したとき、重複は人が直せるが**消失は直せない**。
>   消し残しがあれば `partial` と言う（古い行が残っている）
> - **同じ文が複数あるときは直さない。** どれを直すか決まらないまま当てにいくと、別の行を壊す
> - **承認の後に、もう一度同じ文で探す。** その間に誰かが直していたら見つからず、
>   書き換えは起きない（**承認したときと違うものを上書きしない**）
> - **種別は変えない。** 箇条書きは箇条書きのまま、文言だけ直す
>
> `irreversible_write` にはしなかった。Notion 側にページ履歴があり**人は戻せる**ので、
> そこを根拠に `external_write` として扱い、**差分を見せること**で担保する。
> ただし**削除は入れていない**——消すのは戻せる話とは別で、必要になってから決める。


> [!IMPORTANT] **決定（2026-08-13）: 会議に「入る」のは外へ出る行為。参加は承認、退出は自由。**
> 会議に参加すると**参加者一覧に名前が出て、その場の全員に見える**。だから `external_send`
> として扱い、実行の前に人の承認が要る。承認画面には**どの会議に入るか**を出す。
>
> **抜けるのに承認は要らない**（`internal_write`）。止める方向の行為に承認を挟むと
> 「出たいのに出られない」が起きる。キルスイッチと同じ考え方（§12-4）。
>
> **どうやって入るかはプロバイダで差し替える。** Google Meet Media API は申請と承認が要り、
> 可否が外の事情で決まる。**それを待たずに中身を作れる**ように、偽のプロバイダで
> 通しの試験ができる形にしてある（`surface-cli` と同じ考え方）。
>
> **文字起こしは、取っただけでは記憶に入らない。** 受け取った発言はプロセス内に溜まり、
> 明示的に取り出したときだけ会話へ出る。**何をどこまで残すかは未決**なので、
> 既定では溢れない形にしてある。溢れた分を捨てたときは `partial` と言う（全部見たとは言わない）。
>
> 参加者一覧に出ること自体が、**見られていることが見えている**という担保でもある——
> 会議後に黙って全文を読むより筋が通っている。

> [!IMPORTANT] **決定（2026-08-21）: Google は「共有されたものだけ読む」形で入れる。**
> 会議の文字起こしは Google ドキュメントとして Drive に入るので、**Meet の API を使わずに
> 読める**。境界は**共有設定そのもの**で、Bob に共有されていないものは探しても出てこない——
> 権限の説明が「共有したかどうか」で済む（Notion の統合と同じ考え方）。
>
> Meet Media API（会議に入って音声を受け取る）は採らなかった。**会議の全参加者が
> Developer Preview に登録されている必要があり**、社外ゲストが1人いれば成立しない。
> ドメイン全体の委任も採らなかった——**なりすます相手を絞れず**、やりたいこと
> （共有された文書を読む）に対して権限が過大である。
>
> **アプリと身元を分ける。** OAuth クライアントは全個体で共有し、**リフレッシュトークンだけが
> 個体ごと**になる。Google では身元がアカウント側にあるので、それで「その個体に共有された
> ものしか見えない」が成立する。**Slack とは形が違う**——あちらはアプリ自体が個体なので、
> 個体ごとに別アプリを作っている（B-2 決定）。この違いは後から必ず疑問になるので明記しておく。
>
> 読み取りだけを支給する（§9.3 の段階的解放）。書き込みは `external_write` になり、
> Notion で通した承認の設計に乗せる話になる。

> [!IMPORTANT] **決定（2026-08-24）: 探し方は「名前 → 本文」の順にする。**
> 最初は名前でしか引いていなかった。全文検索は**会議の文字起こしに当たりすぎる**からで、
> 本文が長いぶん、探している会議とは関係のない文書が雑談の一語で並んでしまう。
>
> だが実際に使うと**名前だけでは取りこぼした**。議事録の名前は
> 「Meet: 〈会議名〉 - 日付 - Gemini によるメモ」のように機械が付けるので、
> 人が覚えている呼び名と一致しない。
>
> 両方を立てるために**順番**にした。名前で1件でも出たらそれを返す（当たりすぎはここで止まる）。
> 0件のときだけ本文で引き直す。どちらで当たったかは結果に残す——「名前には無いが本文に
> 出てくる」と言えるかどうかで、人の納得が変わる。
>
> **本文の引き直しに失敗したときは `partial`。** 名前は0件と言い切れるが、本文は確かめて
> いない。ここを `complete` にすると「探して無かった」に見え、**探せなかったことが消える**。
